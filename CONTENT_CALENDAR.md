## Day 07 — 2026-12-02T21:00:00+05:00

A slow frontend does not automatically need a rewrite.

First identify the problem: initial loading, a slow interaction, an oversized response, unnecessary work, or a confusing workflow. Then measure a representative path and prioritize the change with the clearest user impact.

A new framework can be expensive if the original bottleneck is still there afterward.

For founders, the useful question is not "Which stack is trending?" It is "What is stopping users from completing the important task?"

## Day 08 — 2026-12-03T21:00:00+05:00

React profiling is useful when it explains something users actually feel.

Start with the slow interaction, reproduce it, and use profiling to locate expensive work. Then check the rest of the path: request timing, payload size, layout work and unnecessary updates.

Adding memoization everywhere can make code harder to maintain without fixing the real issue. Optimization should be supported by a before-and-after observation, not by the number of hooks added.

The goal is a responsive workflow, not a screenshot of a profiler.

## Day 15 — 2026-12-10T21:00:00+05:00

In a multi-tenant application, switching organizations is not just changing a label in the header.

Review query keys, client-side state, persisted preferences and in-flight requests. Data from one tenant must not be accidentally displayed in another tenant's interface.

The server must independently enforce tenant isolation. Frontend cache hygiene supports the user experience; it does not replace backend security.

This is an architectural review worth doing before an organization switcher reaches production.
